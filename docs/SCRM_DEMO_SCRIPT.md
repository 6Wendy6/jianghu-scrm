# SCRM MVP Demo Script

本文档用于稳定演示当前 SCRM MVP。演示时建议只讲三条业务故事，不要随机点页面；目标是让观众理解“总部发现问题、门店/导购执行、系统沉淀记录并形成异常闭环”。

## 演示准备

### 环境准备

快速演示可以使用 memory 模式：

```bash
npm run dev:backend
npm run dev
```

需要展示刷新后仍保留数据时，使用 PostgreSQL 模式：

```bash
npm run db:migrate
npm run db:seed
npm run dev:backend:db
npm run dev
```

演示前检查：

```bash
curl http://127.0.0.1:8080/api/health
curl http://127.0.0.1:8080/api/system/status
```

### 开场话术

这套系统是一个面向多门店品牌总部的私域 SCRM MVP。它不直接替代企业微信，而是在企业微信之上补齐门店、导购、客户、资料治理、客户运营、SOP 任务和异常监控的业务层。

当前演示重点不是“功能多”，而是三条闭环：

1. 总部能发现基础资料问题，并推动门店补齐。
2. 导购能围绕新客户完成首次跟进、标签和时间线沉淀。
3. SOP 逾期等风险能进入异常监控，并被总部或门店处理。

## 故事 1：总部治理门店资料缺失

### 故事背景

总部运营发现某些门店资料完整率偏低。比如导购缺企业微信 userId、客户缺跟进人、门店缺关键经营字段。这些基础资料不完整，会影响后续分配、跟进、统计和权限隔离。

### 演示路径

1. 进入总部模式。
2. 打开资料补全中心。
3. 查看全局 P0/P1 资料缺失。
4. 按门店筛选到某个门店。
5. 点开一个导购或客户资料缺失问题。
6. 将补全任务分派给门店。
7. 切换到门店/店家模式。
8. 查看总部派发的补全任务。
9. 补全导购或客户信息。
10. 切回总部模式，查看问题状态和完整率变化。

### 讲解重点

- 资料补全不是“表单美化”，它是后续分配、统计、权限和客户运营的基础。
- 总部不需要逐个问门店要 Excel，而是在系统里按 P0/P1 优先级治理。
- 门店补全后，总部能看到问题减少，形成可检查闭环。

### 可展示页面

- 总部工作台。
- 资料补全中心。
- 异常监控。

### 预期观众感知

观众应该理解：这个系统能先把门店、导购、客户这些底层资料管住，后面的客户运营才不会散。

## 故事 2：门店导购运营新客户

### 故事背景

一个新客户通过门店私域入口进入系统，并被分配给导购。导购需要尽快首次跟进，系统要记录跟进过程、更新客户阶段，并沉淀客户画像。

### 演示路径

1. 进入客户运营中心。
2. 切到门店或导购视角。
3. 找到一个处于待首次跟进或新客阶段的客户。
4. 打开客户详情。
5. 展示客户来源、门店、导购、标签、生命周期阶段。
6. 展示系统推荐的 SOP 任务和素材/话术。
7. 复制或使用推荐话术。
8. 写入一条跟进记录。
9. 将客户阶段流转到跟进中或高意向。
10. 完成首次跟进 SOP 任务。
11. 查看客户时间线，确认跟进、标签或阶段变化被记录。

### 讲解重点

- 导购不是在系统里“记流水账”，而是按客户阶段和 SOP 做下一步动作。
- 跟进记录、标签、阶段变化都会沉淀到客户时间线。
- DB 模式下，这些关键动作已经通过后端持久化，不只是前端假状态。

### 可展示页面

- 客户运营中心。
- 客户详情。
- SOP 任务。
- 素材/话术基础版。

### 可展示接口

- `GET /api/customer-ops/bootstrap`
- `GET /api/customers/{id}`
- `POST /api/customers/{id}/followups`
- `POST /api/sop-tasks/{id}/complete`

### 预期观众感知

观众应该理解：客户进入私域后，不只是被记录下来，而是进入可运营、可跟进、可审计的客户运营流程。

## 故事 3：SOP 逾期异常被总部发现并处理

### 故事背景

总部发现某门店有 SOP 任务逾期，例如新客户没有及时首次跟进，或高意向客户没有按时回访。这类问题如果不被发现，会直接影响转化和客户体验。

### 演示路径

1. 进入总部模式。
2. 打开异常监控。
3. 找到 SOP 逾期异常。
4. 打开异常详情。
5. 展示影响客户、所属门店、负责导购、逾期任务和处理建议。
6. 将异常分派给门店，或总部直接处理。
7. 切到客户运营中心，完成关联 SOP 任务。
8. 回到异常监控，查看异常状态更新。
9. 打开客户详情，查看处理记录或时间线。

### 讲解重点

- 异常监控不是单独的告警页面，它连接客户、门店、导购、任务和处理结果。
- 总部看到的不是抽象数字，而是可定位到具体门店、导购和客户的风险。
- 处理后要留下记录，后续可以复盘门店执行质量。

### 可展示页面

- 异常监控。
- 客户运营中心。
- 客户详情。

### 可展示接口

- `GET /api/operation-exceptions`
- `POST /api/operation-exceptions/{id}/resolve`
- `GET /api/sop-tasks`
- `POST /api/sop-tasks/{id}/complete`

### 预期观众感知

观众应该理解：总部可以发现门店执行风险，门店和导购可以闭环处理，系统留下可追溯记录。

## 收尾话术

当前 MVP 已经完成四件事：

- 业务主线：从客户承接、分配、资料补全到客户运营和异常监控。
- 数据底座：客户运营中心已接 PostgreSQL 持久化。
- 工程底座：开发、测试、迁移、seed、健康检查、系统状态已收口。
- 演示底座：有产品说明、验收清单和固定演示故事。

下一阶段不建议继续堆新模块，而是进入企业微信真实数据接入：

- 接入企业微信配置和权限检测。
- 同步部门、成员、客户联系、活码和客户群。
- 完成回调验签、解密、幂等、重试和死信。
- 让当前 MVP 从 demo 数据进入真实业务数据闭环。

## 演示风险提示

| 风险 | 处理方式 |
| --- | --- |
| 本机 PostgreSQL 15432 旧 volume 密码不一致 | 不要重置 volume，改用 `.env` 写真实 DSN 或用临时测试库 |
| 资料补全中心刷新后状态未持久化 | 说明当前为前端 MVP，后端持久化在后续规划 |
| 真实企业微信同步未完成 | 只讲当前 `config_id` 绑定方向和 doctor/retry 能力，不承诺已完成真实同步 |
| DB 模式启动失败 | 先用 `npm run db:status` 检查连接，再用 memory 模式完成业务演示 |
| 演示随机点太散 | 回到三条故事线：资料治理、新客跟进、异常处理 |
