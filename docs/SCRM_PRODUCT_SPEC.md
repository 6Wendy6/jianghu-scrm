# SCRM MVP Product Spec

## 1. 系统定位

Jianghu SCRM 是面向多门店品牌总部的私域 SCRM MVP。当前版本围绕线下门店私域业务的关键闭环：客户承接、门店/导购基础资料治理、客户分配、客户运营、SOP 任务、素材话术和异常监控。

系统目标不是替代企业微信，而是在企业微信和门店经营之间补齐业务编排层：

- 总部统一治理门店、导购、客户和活码承接规则。
- 门店承接总部分派的资料补全、客户运营和异常处理任务。
- 导购围绕自己负责的客户执行跟进、标签维护、SOP 任务和素材话术使用。
- 后端提供 PostgreSQL 持久化、迁移、seed、健康检查和系统状态检查，支撑可演示、可验收、可继续接真实企微数据的工程化 MVP。

## 2. 目标用户

| 用户 | 业务职责 | 当前 MVP 关注点 |
| --- | --- | --- |
| 总部管理员 | 管理全局规则、数据范围、系统状态 | 看全局数据、检查运行状态、准备后续权限体系 |
| 总部运营 | 运营门店私域、资料治理、客户运营质量 | 发现资料缺失、SOP 逾期、客户分配异常并分派处理 |
| 区域经理 | 管理区域门店执行质量 | 看区域内门店、客户、导购和异常 |
| 门店老板 | 关注本门店客户资产和经营结果 | 看本店客户、导购、资料完整率、任务执行 |
| 门店店长 | 执行门店私域配置、导购管理、异常处理 | 补资料、处理交接、分派导购任务 |
| 导购 | 跟进客户、维护客户画像、完成 SOP | 看自己的客户和任务，写跟进、打标签、用话术 |

## 3. 使用模式

### 总部模式

总部模式用于全局治理和监督。总部可以查看所有门店、活码资产、客户分配记录、资料缺失、客户运营数据、异常监控和系统运行状态。

核心任务：

- 发现门店、店长、导购、客户资料缺失。
- 检查门店店长码和客户分配记录。
- 监控客户首次跟进、SOP 逾期、沉睡客户等异常。
- 下发资料补全和运营处理任务。
- 通过 `/api/health` 和 `/api/system/status` 检查运行状态。

### 门店/店家模式

门店模式用于门店执行和本店客户资产管理。门店只能关注本门店的数据，包括导购池、客户、任务、资料补全和异常处理。

核心任务：

- 补全本门店、店长、导购、客户资料。
- 查看总部分派的资料补全和异常处理任务。
- 管理本店导购客户跟进质量。
- 处理本店 SOP 逾期、首次跟进超时、资料缺失等问题。

### 导购视角

导购视角用于一线执行。导购只看自己负责的客户和任务。

核心任务：

- 查看新客户和待跟进客户。
- 维护客户标签和画像。
- 写跟进记录并推动生命周期流转。
- 完成 SOP 任务，使用素材/话术辅助沟通。

## 4. 核心业务主线

当前 MVP 的核心业务主线如下：

1. 客户通过企业微信活码、门店店长码或门店/导购入口进入私域。
2. 系统记录客户分配结果，保留来源、门店、导购和分配状态。
3. 资料补全中心扫描门店、店长、导购、客户资料完整性，生成 P0/P1/P2 问题。
4. 总部或门店处理资料缺失，降低后续分配、跟进、统计和权限风险。
5. 客户进入客户运营中心，带有生命周期阶段、标签、来源、门店、导购和任务。
6. 导购完成首次跟进、写跟进记录、维护标签，系统沉淀客户时间线。
7. SOP 任务驱动后续跟进、复购培育、沉睡唤醒等运营动作。
8. SOP 逾期、首次跟进超时、资料 P0 缺失、沉睡客户等进入异常监控。
9. 总部、门店、导购按角色范围查看并处理数据。
10. 系统状态和迁移状态通过健康检查接口暴露，便于开发、演示和排障。

## 6. 总部模式说明

总部能看：

- 全部门店、导购、客户和异常。
- 企业微信活码资产、门店店长码、客户分配记录。
- 资料补全中心的 P0/P1/P2 问题。
- 客户运营中心的客户列表、任务、素材和异常。
- 系统健康检查、数据库连接、迁移版本、缺失表检查。

总部能做：

- 按门店、区域、优先级筛选资料缺失。
- 分派资料补全和异常处理任务。
- 查看客户详情、生命周期、标签、跟进和时间线。
- 派发或创建 SOP 任务。
- 处理或关闭异常。

核心关注指标：

- 门店资料完整率。
- 新客户首次跟进完成率。
- SOP 逾期数和处理时长。
- 客户生命周期分布。
- 高意向客户、沉睡客户、流失客户数量。
- 数据库连接和迁移状态。

## 7. 门店模式说明

门店能看：

- 本门店导购、客户、任务、异常和资料缺失。
- 本门店相关的客户分配和客户运营数据。
- 总部分派给本门店的处理事项。

门店能做：

- 补全门店、店长、导购、客户资料。
- 分派本店导购的客户运营任务。
- 处理本店 SOP 逾期、首次跟进超时、资料缺失异常。
- 查看本店客户生命周期和跟进质量。

核心执行任务：

- 保证门店和导购基础资料可用于分配、统计和权限过滤。
- 推动导购及时完成首次跟进和 SOP。
- 对本店异常做闭环处理。

## 8. 导购视角说明

导购只能看自己的客户和任务。当前后端通过请求头中的角色、区域、门店、导购标识实现轻量数据范围过滤，DB 模式下无权限访问客户详情会返回 `403 forbidden`。

导购能做：

- 查看自己负责的客户列表和客户详情。
- 添加客户标签。
- 写跟进记录。
- 推动客户生命周期阶段流转。
- 完成、忽略或处理分配给自己的 SOP 任务。
- 使用客户运营中心中的素材/话术。

导购不能做：

- 查看全部门店客户。
- 修改全局规则。
- 查看或处理不属于自己的客户详情。

## 9. 权限矩阵

| 角色 | 数据范围 | 客户查看 | 标签/跟进 | SOP 任务 | 异常处理 | 系统状态 |
| --- | --- | --- | --- | --- | --- | --- |
| `headquarters_admin` / `hq_admin` | 全部 | 全部客户 | 可操作 | 可创建/处理 | 可处理全部 | 可查看 |
| `headquarters_operator` | 全部或指定区域 | 范围内客户 | 可操作 | 可创建/处理 | 可处理范围内 | 可查看 |
| `regional_manager` | 指定区域 | 区域内客户 | 可操作 | 可处理 | 可处理区域内 | 通常只读 |
| `store_owner` / `store_manager` | 指定门店 | 本店客户 | 可操作 | 可处理本店 | 可处理本店 | 通常只读 |
| `guide` | 指定导购 | 自己负责客户 | 可操作自己的客户 | 可处理自己的任务 | 通常只看关联异常 | 不建议开放 |

当前说明：

- 客户运营中心的后端权限过滤已经集中在 permission 层。
- 组织、角色、菜单、字段级权限仍属于后续企业微信集成中心和权限中心规划。

## 10. 客户生命周期定义

当前 MVP 支持围绕客户运营的阶段流转。文档统一定义如下，前端/后端可继续收敛展示命名：

| 阶段 | 含义 | 常见触发 |
| --- | --- | --- |
| 新线索 | 有初始客户线索，但关系和资料未完全确认 | 手工新增、活动导入 |
| 已加企微 | 已建立企业微信好友或可运营关系 | 企微回调、手工标记 |
| 待分配 | 客户进入池中但未确定主跟进人 | 活码/回调未完成分配 |
| 已分配 | 已有门店或导购归属 | 分配规则、店长分派 |
| 待首次跟进 | 已分配但导购尚未完成首次沟通 | 新客承接 SOP |
| 跟进中 | 已有跟进记录，仍在培育 | 导购写入跟进 |
| 高意向 | 明确有购买或到店意向 | 标签、行为、跟进结论 |
| 已成交 | 已记录成交或订单 | 成交记录 |
| 复购客户 | 已成交且进入复购培育 | 复购 SOP |
| 沉睡客户 | 长时间未互动或未跟进 | 逾期扫描、规则判断 |
| 流失客户 | 客户关系流失或明确不再跟进 | 删除导购、流失标记 |
| 黑名单 | 不再触达或需风险隔离 | 人工标记 |

## 11. SOP 任务规则

SOP 任务用于把客户运营动作变成可分派、可完成、可审计的任务。

任务类型：

- 首次跟进。
- 高意向跟进。
- 复购回访。
- 沉睡唤醒。
- 资料补全协同。
- 总部临时派发任务。

任务状态：

- 待处理。
- 处理中。
- 已完成。
- 已忽略。
- 已逾期。

逾期规则：

- 任务存在截止时间。
- 超过截止时间仍未完成时，可进入异常监控。
- 处理任务时写入任务日志和客户时间线。
- 与异常关联的任务完成后，可以同步解决相关异常。

当前实现：

- 客户运营中心的 SOP 任务已具备后端 API 和 PostgreSQL 持久化。
- DB 模式下任务完成会写入 `sop_task_logs` 和 `customer_operation_timeline`。

## 12. 资料补全规则

资料补全中心用于提前治理后续分配、跟进、统计和权限依赖的基础资料。

对象类型：

- 门店。
- 店长。
- 导购。
- 客户/用户。

规则等级：

- P0：会阻断分配、跟进、权限或统计的关键字段缺失。
- P1：会影响运营效率或后续分析的重要字段缺失。
- P2：建议补全的辅助字段缺失。

处理方式：

- 总部查看全局缺失。
- 按区域、门店、对象类型、优先级筛选。
- 分派给门店或责任人。
- 门店补全资料。
- 系统记录处理状态和日志。

当前边界：

- 资料补全中心目前主要是前端 MVP 状态和演示闭环。
- 资料质量规则、问题、快照和变更日志的后端持久化属于后续工作。

## 13. 异常监控规则

异常监控用于让总部和门店发现“业务链路断点”。

异常类型：

- 分配异常：客户进入私域后未成功分配到门店或导购。
- 资料异常：门店、店长、导购、客户存在 P0 资料缺失。
- SOP 逾期：任务超过截止时间仍未完成。
- 首次跟进超时：新客户分配后未及时完成首次跟进。
- 沉睡客户：长时间无互动或无跟进。
- 企微集成异常：活码更新、access token、回调处理等失败，当前主要以 doctor/retry 原型呈现。

进入规则：

- 客户运营相关异常可由后端任务和操作状态生成。
- 资料异常来自资料补全中心扫描结果。
- 企微异常将在真实企业微信接入后进一步完善。

处理规则：

- 异常有状态。
- 处理后保留处理记录。
- 与客户相关的处理应写入客户时间线或任务日志。

## 14. 数据看板指标

总部关注：

- 全部门店客户入池数。
- 客户分配成功率。
- 资料完整率。
- 首次跟进完成率。
- SOP 逾期数。
- 高意向客户数。
- 异常总数和处理率。
- 系统模式、DB 连接、迁移版本。

门店关注：

- 本店新增客户。
- 本店导购跟进完成率。
- 本店待处理任务。
- 本店资料缺失。
- 本店 SOP 逾期和客户沉睡风险。

导购关注：

- 我的客户数。
- 今日新增客户。
- 待首次跟进客户。
- 待完成 SOP 任务。
- 高意向客户。
- 最近跟进和客户时间线。

## 15. 当前 MVP 边界

当前版本已经具备：

- 可演示的前端原型。
- 客户运营中心后端 API。
- 客户运营 PostgreSQL 持久化。
- Repository / Service / Permission 分层。
- 关键客户运营动作的事务闭环。
- 后端行为测试和 DB 行为测试。
- 开发、测试、迁移、seed、健康检查、系统状态检查脚本。

当前仍是 MVP，不是最终生产发布包：

- 企业微信真实同步尚未完整接入。
- 企微回调验签、加解密、消息去重、外部接口限流仍需完善。
- 资料补全中心尚未完整后端持久化。
- 完整组织、角色、菜单、字段级权限中心尚未落地。
- 营销活动中心、完整社群运营、AI 助手、复杂 BI 报表、多租户套餐和移动端不在当前 MVP 范围。

## 16. 后续规划

下一阶段建议继续推进企业微信真实数据同步。当前企业微信集成中心已具备配置脱敏保存、token 缓存状态、权限检测、doctor、错误解释、重试任务和系统状态摘要；后续继续补齐真实同步：

- 企业微信配置中心持续增强。
- 权限检测和 doctor 检查持续增强。
- 部门/成员同步。
- 客户联系同步。
- 活码资产同步。
- 门店店长码与企微 `config_id` 的真实绑定和更新。
- 客户群同步。
- 回调验签、解密、幂等、重试和死信处理。

后续业务扩展：

- 营销活动中心。
- 社群运营增强。
- AI 话术助手。
- AI 客户画像总结。
- 更完整的报表和经营分析。
- 资料补全中心后端持久化。
- 组织/角色/权限中心。
